# TDD Rule

> **이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.**
> 판단이 필요하다고 느끼는 순간이 바로 규칙을 지켜야 하는 순간이다.
> 예외를 만들고 싶으면 규칙을 우회하지 말고 **사용자에게 물어라.**

## 0. 우선순위

이 파일은 **기본값(fallback)** 이다.

프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD·테스트 규칙이 있으면 **그쪽이 우선한다.** 테스트 명령어, 테스트 파일 위치, 커버리지 기준, 네이밍 규칙은 항상 프로젝트 문서에서 먼저 확인하라. 프로젝트 문서에 없는 항목만 이 파일을 따른다.

## 1. 적용 기준

### TDD를 반드시 적용한다

- **비즈니스 로직** — 계산, 분기, 상태 전이, 도메인 규칙
- **API / 엔드포인트** — 요청 검증, 응답 형태, 상태 코드, 에러 매핑
- **유틸 · 순수 함수** — 파싱, 포매팅, 변환, 정규화
- **버그 수정** — **버그를 재현하는 실패 테스트를 먼저 쓴다.** 재현 테스트 없는 버그 수정은 수정이 아니라 추측이다
- **리팩터링** — 시작 전에 기존 동작을 고정하는 테스트가 있어야 한다. 없으면 먼저 만든다

### TDD가 불필요하다

- **타입 정의** — 인터페이스, 타입 별칭, 스키마 선언
- **설정 파일** — 빌드·린트·CI 설정, 환경 변수 정의
- **순수 UI** — 로직 없는 마크업, 스타일, 레이아웃
- **SQL / 마이그레이션** — 스키마 DDL 자체
- **자동 생성 코드** — 코드젠 산출물

**경계 판단:** UI라도 조건 분기·상태 계산이 들어가면 그 부분은 로직이다. 함수로 분리해서 TDD를 적용하라. "UI라서 뺐다"는 로직을 컴포넌트 안에 묻어둔 변명이 되기 쉽다.

## 2. RED — 실패하는 테스트

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 넣지 마라
- 테스트 이름은 **동작을 서술**한다. "works", "test1" 금지
- **반드시 실행해서 실패를 눈으로 확인한다.** 실행하지 않은 RED는 RED가 아니다
- **실패 이유가 "기능 미구현"이어야 한다.** 오타, import 오류, 문법 오류로 인한 실패는 RED가 아니다 — 고치고 다시 실행하라
- 실패 메시지가 무엇이 잘못됐는지 말해주는지 확인한다

## 3. GREEN — 최소한의 코드

- **테스트를 통과시키는 최소한의 코드만 쓴다.** 그 이상은 전부 위반이다
- **YAGNI.** 지금 테스트가 요구하지 않는 것은 만들지 않는다 — 미래의 인자, 미래의 분기, 미래의 추상화, 미래의 설정 옵션
- 하드코딩으로 통과시켜도 된다. 다음 RED가 그것을 깨뜨릴 것이다
- **신규 테스트 + 기존 테스트 전체를 실행해 모두 통과하는지 확인한다.** 신규만 돌리고 넘어가지 마라

## 4. REFACTOR — 구조 개선

- 허용: **중복 제거, 이름 개선, 헬퍼 추출, 구조 정리**
- **새 동작을 추가하지 마라.** 새 동작은 새 RED에서 시작한다
- 리팩터링 중에는 **테스트를 수정하지 않는다.** 테스트를 고쳐야 통과한다면 그것은 리팩터링이 아니라 동작 변경이다
- **각 단계마다 테스트를 실행해 green을 유지한다.** 한 번에 크게 바꾸고 마지막에 돌리지 마라
- 개선할 게 없으면 건너뛴다. 억지 추상화는 위반이다

## 5. REPEAT

다음 동작에 대한 **RED로 돌아간다.** 기능이 완성될 때까지 사이클을 반복한다.

한 사이클은 작게 유지한다. RED에서 GREEN까지 오래 걸린다면 테스트가 너무 큰 것이다 — 쪼개라.

## 6. 삭제 강제 규칙

**테스트보다 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작한다.**

- **"참고용"으로 남겨두는 것도 금지.** 주석 처리, 별도 파일 이동, 브랜치 보관, 스크래치패드 복사 전부 위반이다
- 눈앞에 답이 있으면 그 답에 맞춘 테스트를 쓰게 된다. 그 순간 테스트는 설계 도구가 아니라 사후 승인 도장이 된다
- 삭제 후 다시 쓰는 코드는 대개 더 작다. 그게 이 규칙의 목적이다
- **삭제했다는 사실을 사용자에게 보고하라.** 조용히 지우지 마라

## 7. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순하면 테스트는 30초면 끝난다. 시간이 이유가 될 수 없다. 그리고 단순하다는 판단 자체가 자주 틀린다 |
| "나중에 추가하겠다" | 나중에 쓰는 테스트는 코드를 검증하지 않고 **코드를 추인한다.** 이미 있는 구현에 맞춰 쓰기 때문에 버그까지 함께 고정된다 |
| "시간이 없다" | TDD는 디버깅 시간을 앞당겨 쓰는 것이지 추가로 쓰는 게 아니다. 시간이 없을수록 되돌아오는 비용이 크다 |
| "삭제하면 낭비" | 매몰 비용이다. 이미 쓴 시간은 남기든 지우든 돌아오지 않는다. 남기면 테스트 품질까지 함께 잃는다 |
| "프로토타입이다" | 프로토타입이 그대로 운영에 올라가는 것은 예외가 아니라 기본값이다. 진짜 버릴 코드라면 **버린다고 명시하고 커밋하지 마라** |
| "테스트하기 어려운 코드다" | 테스트하기 어렵다는 것은 설계 문제의 신호다. 그것이 TDD가 알려주려는 바로 그 정보다. 부수효과에서 로직을 분리하라 |
| "기존 코드에 테스트가 없다" | 기존 코드 전체를 덮으라는 게 아니다. **네가 지금 건드리는 범위**만 덮으면 된다 |

## 8. 위반 시

규칙을 어겼다는 것을 인지하면, 계속 진행하지 말고 **즉시 멈추고 사용자에게 알린다.** 어긴 지점과 되돌릴 방법을 함께 제시하라. 위반을 숨기고 완료를 보고하는 것이 가장 무거운 위반이다.
