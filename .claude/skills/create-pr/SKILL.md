# create-pr: 브랜치 정리 후 PR 생성

커밋된 변경사항을 push하고 PR을 생성한다. 커밋 메시지와 diff를 읽어 PR 제목·본문을 쓰고, 저장소 언어에 맞는 템플릿을 골라 채운다.

**이 스킬은 `context: fork`로 격리 실행되므로 대화 맥락이 없다.** 왜 이 변경을 했는지, 사용자가 무엇을 의도했는지 알 수 없다. 그래서 판단 근거는 전부 저장소에서 직접 읽어야 한다 — 커밋 메시지, diff, `AGENTS.md`, 기존 PR 히스토리. 추측으로 배경을 지어내지 마라. 커밋에서 읽어낼 수 없는 "왜"는 비워두고 마지막 보고에 "배경은 작성자가 보강 필요"로 남기는 것이 낫다. 지어낸 배경은 리뷰어를 잘못된 방향으로 보낸다.

같은 이유로 **실행 중에 사용자에게 질문할 수 없다.** 애매한 지점은 안전한 쪽(draft PR, 좁은 범위)을 골라 진행하고, 무엇을 어떻게 판단했는지 마지막 보고에 밝혀 사용자가 고칠 수 있게 한다.

또한 격리 실행에서는 **마지막 메시지 하나만 호출자에게 전달된다.** 끝났다는 사실을 알리는 메시지마다 보고 전문을 다시 실어야 하며, 자세한 이유와 방법은 아래 "보고는 매번 전문으로 쓴다"에 있다.

## 워크플로우

### Step 0: 저장소 지침 로드

저장소 루트의 `AGENTS.md`(없으면 `CLAUDE.md`)를 읽는다. 여기서 얻을 것:

- **빌드·린트·테스트 명령** — Step 5 검증에 그대로 쓴다. 명령을 추측해 지어내지 마라.
- **커밋·PR 컨벤션** — 타입 접두사, 언어, scope 사용 여부.
- **push·배포 관련 제약** — "공개 배포하면 안 된다", "특정 브랜치에 직접 push 금지" 같은 조항이 있으면 따른다.

모노레포처럼 하위 디렉토리에 중첩 `AGENTS.md`가 있으면 변경된 파일에 가장 가까운 것이 우선한다.

### Step 1: 상태 파악

한 번에 실행해 전체 그림을 잡는다.

```bash
git status --short
git branch --show-current
gh repo view --json nameWithOwner,defaultBranchRef,isFork
git log --oneline -20
```

**미커밋 변경이 있으면 여기서 멈춘다.** 커밋하지 않는다. PR은 커밋된 것만 담기므로, 미커밋 변경을 남긴 채 PR을 열면 사용자는 자기 작업이 포함됐다고 착각한다. `commit` 스킬로 먼저 커밋하거나 stash한 뒤 다시 실행하라고 안내하고 종료한다. 사용자의 작업을 임의로 stash하거나 커밋하지 마라.

예외: 변경이 추적되지 않는 로컬 산출물(로그, `.DS_Store` 등)뿐이고 gitignore 대상이 마땅한 경우에는 진행해도 된다. 단 무엇을 남겨뒀는지 보고에 적는다.

### Step 2: base 브랜치와 토픽 브랜치 확정

**base 브랜치**는 `--base` 인자 → 저장소 default branch 순으로 정한다. fork 저장소라면 upstream이 아니라 사용자 소유 저장소의 default branch를 기본으로 삼는다(권한 없는 곳에 PR을 열어 실패하는 것을 막는다).

**현재 브랜치가 base와 같으면** 토픽 브랜치를 파생한다. base에서 base로는 PR을 열 수 없다.

1. base가 이미 원격에 push된 커밋과 로컬 커밋을 비교해 PR에 담길 커밋을 확정한다: `git log origin/<base>..HEAD --oneline`
2. 담길 커밋이 없으면 PR을 만들 것이 없다. 그렇게 보고하고 종료한다.
3. 담길 커밋에서 브랜치명을 짓는다: `<type>/<slug>`
   - `type`은 커밋들의 지배적인 conventional commit 타입(`feat`, `fix`, `chore`, `refactor`).
   - `slug`는 **영문 kebab-case**로 짓는다. 한글 브랜치명도 git에서 동작하지만 URL·CI 설정·터미널에서 깨지는 도구가 많아 실무 비용이 크다. 한국어 커밋에서 핵심 명사를 뽑아 영문으로 옮긴다. 예: `feat: 프롬프트 500자 길이 제한 추가` → `feat/prompt-length-limit`
4. `git switch -c <브랜치명>`으로 파생한다. base 브랜치는 그 커밋들을 그대로 들고 있게 되므로, **base를 되돌리지 마라** (`git reset`은 사용자가 명시적으로 요청할 때만). base에 남은 커밋을 어떻게 정리할지는 사용자의 판단이다 — 보고에 그 사실을 적어 알려준다.

현재 브랜치가 base가 아니면 그 브랜치를 그대로 쓴다.

### Step 3: 템플릿 선택

우선순위대로 결정한다.

1. **저장소 자체 PR 템플릿이 있으면 그것을 쓴다.** `.github/PULL_REQUEST_TEMPLATE.md`, `.github/pull_request_template.md`, `.github/PULL_REQUEST_TEMPLATE/` 디렉토리를 확인한다. 팀이 합의해 만든 형식이 번들 템플릿보다 우선한다.
2. `--ko` / `--en` 인자가 있으면 그것을 따른다.
3. 없으면 **저장소의 언어를 감지**한다. 최근 커밋 제목 20개와 기존 PR 제목·본문 몇 개(`gh pr list --limit 10 --json title,body`)에서 한글 음절이 뚜렷하게 나타나면 한국어, 아니면 영어로 판단한다.
   - 한국어 → `references/pr-template-ko.md`
   - 영어 → `references/pr-template-en.md`

언어 감지를 경로나 저장소 이름으로 하지 마라. 사내 저장소가 영어를 쓸 수도, 개인 저장소가 한국어를 쓸 수도 있다. **실제로 쓰인 글이 근거다.**

고른 템플릿 파일을 읽고 그 안의 지시를 따른다.

### Step 4: 제목과 본문 작성

**제목**은 저장소 히스토리의 스타일을 따른다. 커밋이 conventional commits를 쓰면 PR 제목도 `<type>: <요약>` 형태로 맞춘다. 커밋이 하나면 그 제목을 그대로 쓸 수 있다. 여러 개면 개별 커밋 제목의 나열이 아니라 **전체를 아우르는 한 줄**로 쓴다.

제목 언어는 Step 3에서 고른 템플릿 언어와 맞춘다.

**본문**은 템플릿 골격을 채운다. 채울 재료는 이렇게 모은다:

```bash
git log origin/<base>..HEAD --format='%s%n%n%b'   # 커밋 메시지 본문에 "왜"가 있다
git diff origin/<base>...HEAD --stat              # 변경 규모와 범위
git diff origin/<base>...HEAD                     # 실제 변경 (크면 핵심 파일만)
```

커밋 메시지 본문(`%b`)이 이 스킬이 얻을 수 있는 "왜"의 가장 좋은 출처다. 커밋을 잘 쓴 저장소라면 배경 섹션 대부분이 거기서 나온다.

본문을 셸 명령에 보간하지 마라. 파일로 쓰고 `--body-file`로 넘긴다(Step 6). 커밋 메시지에 백틱·`$`·따옴표가 섞여 있을 때 명령이 깨지거나 의도치 않게 실행되는 것을 막는다.

### Step 5: 검증

Step 0에서 찾은 빌드·린트·테스트 명령을 실행한다. 실행 코드가 바뀌지 않은 PR(문서·설정만)이라면 생략해도 되지만, 생략했다는 사실을 본문 검증 섹션과 보고에 적는다.

**검증이 실패하면 push하지 않고 PR도 만들지 않는다.** 실패 내용을 그대로 보고하고 종료한다. 깨진 코드로 PR을 열면 리뷰어의 시간이 먼저 소모되고, CI 실패 알림이 팀에 퍼진다. 되돌리는 비용이 멈추는 비용보다 크다.

저장소에 감지되는 검증 수단이 아예 없으면 그 사실을 보고에 적고 진행한다. **없는 검증을 지어내 통과했다고 쓰지 마라.**

### Step 6: push와 PR 생성

```bash
git push -u origin <브랜치명>
gh pr create --base <base> --title "<제목>" --body-file <본문파일> --draft
```

- **`--draft`가 기본값이다.** 이 스킬은 격리 실행되어 사용자 재가를 받을 수 없고, PR은 팀에게 보이는 외부 산출물이다. draft로 열면 리뷰 요청 알림이 나가지 않아, 사용자가 제목·본문을 고친 뒤 직접 ready로 바꿀 수 있다. `--ready` 인자가 있을 때만 draft를 뗀다.
- **force push하지 않는다.** `git push --force`가 필요한 상황(리베이스된 브랜치 등)이면 push하지 말고 그 사실을 보고한다. 남의 커밋을 지울 수 있는 명령은 사용자 판단 영역이다.
- 해당 브랜치에 **이미 열린 PR이 있으면** 새로 만들지 않는다. push만 하고(그러면 기존 PR이 자동 갱신된다) 기존 PR URL을 보고한다.
- reviewer·label·assignee는 사용자가 요청하지 않았으면 **붙이지 않는다.** 임의로 지정한 리뷰어에게 알림이 가는 것은 되돌릴 수 없다.

## 보고 형식

```
PR 생성 완료 (draft)

  https://github.com/<owner>/<repo>/pull/<번호>

  제목:   feat: 프롬프트 500자 길이 제한 추가
  브랜치: feat/prompt-length-limit → main
  커밋:   3개
  템플릿: 한국어 (커밋 히스토리에서 감지)
  검증:   build ✓  lint ✓  test ✓ (26 passed)

판단한 것:
  - main에 있던 커밋 3개를 feat/prompt-length-limit로 파생했습니다.
    main에는 그 커밋이 그대로 남아 있으니 정리가 필요하면 알려주세요.
  - draft로 열었습니다. 내용을 확인한 뒤 ready로 바꾸세요.
```

"판단한 것"에는 사용자에게 물었어야 하지만 격리 실행이라 스스로 정한 것들을 적는다 — 브랜치명, 템플릿 언어, 범위에서 뺀 것, 검증 생략 여부. 아무것도 없으면 이 블록을 생략한다.

중간에 멈춘 경우에는 어디까지 진행했고 왜 멈췄는지, 사용자가 무엇을 하면 되는지를 적는다.

### 보고는 매번 전문으로 쓴다

**호출자에게 전달되는 것은 마지막 메시지 하나뿐이다.** 격리 실행이라 중간에 쓴 내용은 호출자가 볼 수 없고, 앞선 턴에서 아무리 잘 보고했어도 그 뒤에 짧은 메시지를 한 줄 더 쓰면 **그 한 줄이 결과를 덮어쓴다.**

작업을 끝낸 뒤에도 훅 알림이나 추가 입력으로 다시 호출될 수 있다. 그때 이렇게 답하지 마라:

```
완료했습니다. 더 진행할 것은 없습니다.
대기 중입니다. 새 요청을 주세요.
이미 보고했습니다.
```

이런 응답은 호출자 입장에서 **PR이 만들어졌는지조차 알 수 없는 결과**가 된다. 실제로 PR URL을 돌려받지 못해 호출자가 `gh`로 직접 확인해야 했던 사례가 있다.

대신 **끝났다는 사실을 알리는 모든 메시지에 위 보고 형식을 통째로 다시 싣는다.** 같은 내용을 반복하는 것이 어색해 보여도, 반복은 비용이 거의 없고 누락은 결과를 통째로 잃는다. 반복임을 알리는 한 줄을 앞에 붙이되, **줄이거나 생략하지 않는다.** 두 번째 보고도 첫 번째와 글자 수가 같아야 한다:

```
(앞서 보고한 내용과 동일합니다)

PR 생성 완료 (draft)

  https://github.com/acme/webapp/pull/482

  제목:   feat: 프롬프트 500자 길이 제한 추가
  브랜치: feat/prompt-length-limit → main
  커밋:   3개
  템플릿: 한국어 (커밋 히스토리에서 감지)
  검증:   build ✓  lint ✓  test ✓ (26 passed)

판단한 것:
  - main에 있던 커밋 3개를 feat/prompt-length-limit로 파생했습니다.
    main에는 그 커밋이 그대로 남아 있으니 정리가 필요하면 알려주세요.
  - draft로 열었습니다. 내용을 확인한 뒤 ready로 바꾸세요.
```

URL을 `https://github.com/...`처럼 줄여 쓰거나 뒷부분을 `...`으로 잘라내지 마라. 호출자는 그 문자열을 그대로 받으므로, 생략된 URL은 URL이 아니라 잡음이다.

작업을 시작하지 못했거나 중간에 멈춘 경우도 마찬가지다 — "미커밋 변경이 있어 중단했습니다"라는 사실과 사용자가 할 일을 매 메시지에 다시 적는다. **최소한 PR URL(또는 왜 없는지)은 어떤 메시지에서도 빠지면 안 된다.**

## 규칙

- **커밋하지 않는다.** 커밋은 `commit` 스킬의 영역이다. 미커밋 변경이 있으면 Step 1에서 멈춘다.
- **base 브랜치에 직접 push하지 않는다.** 이 스킬의 결과물은 항상 토픽 브랜치와 PR이다.
- **draft가 기본, ready는 명시적 요청일 때만.**
- **`git add -A` / `git add .`를 쓰지 않는다.** 이 스킬은 애초에 stage할 일이 없다.
- `--amend`, `reset`, `rebase`, `push --force`, `checkout --` 등 히스토리나 작업물을 되돌리는 명령은 사용자가 명시적으로 요청할 때만 쓴다.
- PR 본문에 **시크릿·토큰·`.env` 내용·API 키를 넣지 않는다.** diff에 그런 값이 섞여 있으면 PR을 만들지 말고 그 사실을 먼저 보고한다. PR 본문은 저장소 히스토리에 남고, 공개 저장소면 즉시 외부에 노출된다.
- 저장소가 공개(public)인지 확인하고, 공개 저장소에 처음 PR을 여는 경우 보고에 그 사실을 적는다. 무엇이 외부에 보이는지 사용자가 알아야 한다.
- 커밋할 것도 push할 것도 없으면 그렇게 말하고 끝낸다.

## 인자

- `--ko` / `--en`: 템플릿 언어를 강제한다. 기본값은 저장소 언어 자동 감지(Step 3).
- `--ready`: draft가 아닌 일반 PR로 생성한다.
- `--base <브랜치>`: base 브랜치를 지정한다. 기본값은 저장소 default branch.
- 나머지 인자는 제목 힌트로 해석한다. 힌트가 diff와 맞지 않으면 그대로 쓰지 말고 조정한 뒤 이유를 보고에 밝힌다.
