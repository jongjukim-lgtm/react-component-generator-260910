# commit: 변경사항 분석 후 컨벤션 커밋

변경사항을 훑어보고 논리적 단위로 묶은 뒤, 한국어 커밋 메시지를 작성해 바로 커밋한다. 사용자에게 확인을 묻지 않고 Step 1~4를 끝까지 진행하고, 무엇을 어떻게 커밋했는지는 마지막에 보고한다.

## 워크플로우

### Step 1: 변경사항 분석

다음을 한 번에 실행해 전체 상태를 파악한다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -15
```

확인할 것:

- 이미 staged된 변경이 있는가 → 있으면 사용자가 의도적으로 골라둔 것으로 보고, 기본적으로 그 범위만 커밋한다.
- `git log`에서 이 저장소가 실제로 쓰는 메시지 스타일(타입 접두사, scope 사용 여부, 언어)을 확인한다. 아래 컨벤션보다 **저장소의 실제 히스토리가 우선**이다.
- 커밋하면 안 되는 파일이 섞여 있는지 본다: `.env`, 키·토큰·비밀번호가 담긴 파일, 빌드 산출물, 대용량 바이너리, 임시 디버그 코드. **승인 절차가 없으므로 이 판단은 여기서 끝난다** — 해당하는 것은 stage하지 않고 제외한 채 나머지를 커밋한 뒤, 무엇을 왜 뺐는지 마지막 보고에 적는다.
- 판단이 애매한 파일(비밀정보인지 아닌지 확실하지 않은 경우)은 **제외 쪽으로 기운다.** 빠뜨린 커밋은 한 번 더 하면 되지만, 올라간 비밀정보는 히스토리에 남는다.

diff가 너무 커서 다 읽기 어려우면 `git diff --stat`으로 먼저 윤곽을 잡고, 핵심 파일만 골라 전체 diff를 본다.

### Step 2: 논리적 단위로 분류

변경을 "하나의 의도" 단위로 묶는다. 기준:

- 목적이 다르면 나눈다 — 기능 추가와 그 과정에서 발견한 버그 수정은 별개 커밋.
- 되돌릴 때 함께 되돌려야 하는 것들은 한 커밋에 둔다.
- 포맷팅·리네이밍 같은 잡음은 기능 변경과 섞지 않는다.
- 억지로 쪼개지 않는다. 실제로 하나의 작업이면 파일이 여러 개여도 한 커밋이다.

### Step 3: 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>
```

scope가 의미를 더할 때만 `<type>(<scope>): <요약>`을 쓴다.

타입:

| type | 용도 |
|------|------|
| `feat` | 새 기능·동작 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `chore` | 설정, 의존성, 빌드, 문서, 스킬 등 그 외 |

요약 작성 규칙:

- 한국어로, 50자 내외.
- 무엇을 했는지 명사형·평서형으로 끝낸다: "예시 프롬프트를 시각적 임팩트 순으로 재배치", "Google 모델 실패 시 자동 폴백 추가".
- 마침표를 붙이지 않는다.
- "수정", "업데이트" 같은 뭉뚱그린 표현 대신 무엇이 어떻게 바뀌는지 쓴다.

본문은 **왜** 필요한지가 요약만으로 전달되지 않을 때만 추가한다. 무엇을 바꿨는지 파일별로 나열하지 않는다 — 그건 diff가 이미 말해준다.

### Step 4: 커밋 실행

묻지 않고 바로 실행한다. "이렇게 커밋할까요?" 같은 확인 질문을 넣지 않는다.

커밋마다 순서대로:

```bash
git add <해당 파일들>
git commit -m "<메시지>"
```

전부 끝나면 `git log --oneline -<n>`으로 결과를 확인하고, 이 형태로 보고한다.

```
커밋 2개 완료

  a1b2c3d  feat: 코드 뷰에 복사 버튼 추가
           src/components/CodeView.tsx, src/App.css
  e4f5g6h  chore: prismjs 의존성 추가
           package.json, package-lock.json

제외: .env (API 키 포함)
```

제외한 파일이 없으면 마지막 줄은 생략한다.

중간에 커밋이 실패하면 거기서 멈춘다. 이미 성공한 커밋은 되돌리지 말고, 어디까지 되었고 왜 멈췄는지 보고한다.

## 규칙

- **승인을 묻지 않는다.** 로컬 커밋은 `git reset --soft HEAD~1`로 언제든 되돌릴 수 있으므로 중간에 멈추지 않고 끝까지 진행한다. 이 자율성은 **커밋까지만** 적용되며, 아래 나머지 규칙은 그대로 유효하다.
- **push하지 않는다.** 사용자가 따로 요청할 때만 한다. push는 되돌리기 어려우므로 자동 실행 대상이 아니다.
- **`git add -A` / `git add .`를 쓰지 않는다.** 의도한 파일만 명시적으로 stage한다.
- `--amend`, `reset`, `rebase`, `checkout --` 등 히스토리나 작업물을 되돌리는 명령은 사용자가 명시적으로 요청할 때만 쓴다.
- pre-commit hook이 실패하면 커밋을 강행(`--no-verify`)하지 말고 실패 내용을 보고한다. hook이 파일을 고쳤다면 그 변경을 확인한 뒤 다시 stage해서 커밋한다.
- 커밋할 변경이 없으면 그렇게 말하고 끝낸다.

## 인자

- `--all`: staged 여부와 관계없이 추적 중인 모든 변경(및 새 파일)을 후보로 삼는다. 기본값은 staged가 있으면 staged만, 없으면 전체.
- 나머지 인자는 메시지 힌트로 해석한다. 힌트가 있어도 diff와 맞지 않으면 그대로 쓰지 말고 조정한 뒤 이유를 밝힌다.
